A distributed file system in Go

This started as a big data course project at USF: build something shaped like HDFS, then run it on the department’s cluster. Mine ran on twelve storage machines named orion01 to orion12, which is why the simulation further down uses those names.

A client cuts a file into 7 MB chunks and sends them to storage nodes. One controller remembers which node holds which chunk, keeps that in a Bitcask store on disk, and makes sure every chunk exists on three nodes. Everything talks protobuf over TCP.

The part I’d show someone first is how the controller picks a home for the next chunk.

Free disk space divided by the number of requests the node has already been handed, highest wins. A big empty machine doesn’t get everything just because it is big.

Six seconds against a five-second heartbeat is tight. One late beat and the controller starts copying data that was never lost.

Failure handling is blunt. Every node sends a heartbeat each five seconds, carrying its free space and request count. The controller looks at the clock every two seconds, and any node that has been quiet for more than six is written off. For each chunk that node held, a surviving copy is told to send itself somewhere new.

You can watch that happen here. Pick a node, stop it, and wait.

A shared canvas without WebSockets

Open a link and you get a room with a six-character ID. Draw, and anyone else holding that link sees your lines appear and can add their own. Someone who turns up late gets the whole drawing replayed to them first.

Every held response sits in one Node process, keyed by username. The README’s first note is “Use unique usernames”, and this is why.

I built it on long polling. Each browser keeps a single POST /wait open, and the server simply doesn’t reply until it has strokes to hand over. Drawing is batched at both ends: the client collects points for 100 ms before sending them, and every 100 ms the server empties its queue into every response that is waiting. The browsers then ask again.

Strokes are also written to MongoDB every three seconds, which is where the replay for latecomers comes from.

A to-do list that changes with the tab

I built this one for myself. A single long list follows you around all day, and most of it has nothing to do with the page in front of you. Todays Tasks keeps a separate list for each website instead. Open it on GitHub and you see GitHub tasks. Open it on Figma and you see Figma tasks. The repository describes it as a simple, fast extension for people with ADHD.

Tasks are matched by their text, which is capped at 30 characters. There are no IDs anywhere.

There is no server behind it. Tasks are saved in the browser first. If you sign in, they also go into one tasks.json in the extension’s own hidden folder in your Google Drive, which is the only part of Drive it is permitted to touch.

When a laptop comes back online, whatever it saved locally is merged into the Drive copy. Where two devices disagree about whether a task is done, the later edit wins, and a small banner tells you how many tasks changed.

Something for the Touch Bar to do

The Touch Bar on my MacBook mostly sat idle, so I wrote a menu bar app that turns it into an audio visualizer for whatever is playing. It has fourteen modes and eight colour themes.

512 samples at 48 kHz is a little under 11 ms, so the picture is never much further behind the sound than that.

Getting at system audio on a Mac normally means installing a virtual audio driver. I used ScreenCaptureKit instead, which can tap whatever is playing with nothing extra installed. The trade is the permission dialog, where macOS asks for “Screen & System Audio Recording”.

From there the samples go through a 4096-point FFT that re-runs every 512 samples. SpriteKit draws the result into a strip 30 points tall, and a private framework, DFRFoundation, puts that strip on the bar.

PintNetwork

In the middle of 2020, hospitals in India were treating some COVID-19 patients with plasma from people who had already recovered. Two doctors in Mumbai, Dr Neil Pinto and Dr Kareena, saw that willing donors and the patients who needed them had no straightforward way to find each other.

They brought the problem and the medical criteria. I wrote the web application, front and back, in about a week.

Donors and patients registered on pintnetwork.com. A donor’s answers were checked against the doctors’ rules, and when a donor and a patient were matched, both got an SMS and an email with what they needed to reach each other.

A donor who fails the check is still saved, only flagged. A person makes the final call, not the form.

Daily Excelsior wrote about it on 13 July 2020. A week after launch, it reported, 66 donors and 65 patients had registered.

I kept working on it after that. The history of the public backend runs to May 2021: matching by city, then by blood group, then a rewrite during the second wave. In that version a coordinator confirms each match from an admin view, and the messages go out from there.

The site is offline now. What is left is the code and the article.

The archive has the rest, including a Kubernetes multi-app template, a Bitly clone and an ISP throttling detector.
